# SafeDrop 요구사항 명세

## 1. 문제 정의
- **누가:** 외부 클라우드(구글 드라이브, 메신저 파일 전송 등)를 쓸 수 없는 기업의 임직원 — 개인정보·민감정보가 담긴 문서를 사내에서 주고받는 인사·영업·개발 부서
- **무엇이 문제인가:**
  1. 파일을 보내기 전에 안에 어떤 개인정보가 있는지 사람이 일일이 확인해야 한다 → 바쁘면 건너뛴다
  2. 같은 파일이라도 **누구에게 보내느냐**에 따라 허용 여부가 다르다 (인사팀 → 원본 가능, 다른 부서 → 가려야 함, 협력사 → 금지). 규정을 외우고 있어야 판단할 수 있다
  3. 번호처럼 형식이 정해진 정보는 기존 도구로 찾을 수 있지만, "○○ 과장 지난주 공황장애 진단" 같은 **문장 속 민감정보**는 놓친다
  4. 막혔을 때 **왜 막혔는지, 어떻게 하면 보낼 수 있는지** 알려주지 않으면 사용자는 우회 경로(개인 메신저)를 찾는다

**해석 — SafeDrop이 들어가는 자리**
- 해킹은 외부 공격을 막는 문제지만, 업무 과실은 **"보내기 직전"에 한 번 더 확인하면 막을 수 있는 유출**이다. 잘못 첨부·동보 발송·단체방 게시 모두 "이 파일을 이 사람(들)에게 보내도 되는가"를 묻지 않아서 생긴다.
- 망분리가 완화되면 "망이 나뉘어 있으니 안전하다"는 전제가 사라지고, **파일 하나하나를 내용과 수신자 기준으로 판단**해야 한다. 반대로 여전히 외부 클라우드를 못 쓰는 기업에는 **사내에서 안전하게 주고받는 채널** 자체가 필요하다. SafeDrop은 두 경우 모두를 대상으로 한다(로컬 LLM으로 외부 전송 없이 동작 — `docs/eval/local_llm.md`).

### 일반적인 DLP와의 차이
개인정보를 찾는 부분은 상용 DLP에서 검증된 방식 — 번호 형식 + 검증식 + 주변 키워드로 신뢰도를 올리는 방식(예: [Microsoft Purview 민감 정보 유형](https://learn.microsoft.com/purview/sensitive-information-type-learn-about)) — 과 같은 계열로 직접 구현했다. SafeDrop이 새로 설계한 것은 **찾은 다음**이다.

| | 일반적인 DLP | SafeDrop |
|---|---|---|
| 탐지 | 형식 + 주변 문맥 + 신뢰도 | 같은 계열로 직접 구현 + AI 문맥 판단 (측정 공개) |
| 결과 | 정책에 따라 차단·경고 | 같은 파일을 **받는 사람마다** 원본 / 가린 사본 / 차단 |
| 설명 | 정책 안내 문구 | 사내 규정 조항 검색 근거 설명(인용 검증 통과분만) + **원문에서 고칠 위치 표시** |
| 전송 | 기존 메일·메신저 경로 감시 | 전송 채널 자체 + 서버 서명 토큰을 받는 쪽 브라우저가 검증 |
| AI | — | 외부로 보내지 않는 로컬 LLM으로도 동작 (GPU 1대, `docs/eval/local_llm.md`) |

※ '일반적인 DLP'는 Microsoft Purview 공개 문서 기준이며 제품마다 기능은 다를 수 있다. 상용 제품에 있는 정확값 대조(EDM)·문서 지문·학습형 분류기는 SafeDrop에 없다.

### 베이스라인(v0) 대비 개선 (측정 근거)
형식 기반 탐지(정규식 + 검증식)를 우리 v0로 먼저 구현하고, 같은 테스트 문서로 개선 폭을 측정했다(`docs/eval/`).
| | 우리 베이스라인 v0 | 최종 |
|---|---|---|
| 정형 개인정보 정밀도 (잘못 잡지 않음) | 69% — 제조번호를 주민번호로, 공용 메일을 개인 메일로 | 96% — 문맥(표 머리글, 법인·공용 여부) 판단 |
| 문장 속 민감정보 재현율 | 0% | 100% (AI 문맥 판단, 경계 사례 2건 보수 판정) |

## 2. 사용자와 시나리오
| 사용자 | 대표 시나리오 |
|---|---|
| 발신자 (임직원) | 인사발령 문서를 인사팀·영업팀·협력사 3명에게 보내려 한다 → 수신자마다 원본/마스킹본/차단으로 나뉘고, 이유와 대안을 설명받는다 |
| 수신자 (임직원·협력사) | 받은 파일이 정말 서버가 허가한 그 파일인지, 나에게 온 것이 맞는지 브라우저가 자동으로 확인해 준다 |
| 정보보호 관리자 | 누가 누구에게 어떤 조치로 보냈는지(내용 없이) 감사 로그로 확인하고, 탐지 성능을 측정한다 |

**사용자 흐름:** 로그인 → 파일 선택 → 수신자 선택 → 검사하기 → 수신자별 판정·근거 조항·AI 설명 확인 → (마스킹본 미리보기) → 허가된 대상에게 전송 → 수신자 브라우저가 검증 후 다운로드

## 3. 기능 요구사항
상태: ✅ 완료 · 🔶 부분 · ⬜ 미구현 / 검증: 자동 테스트(T), 측정 스크립트(M), 배포 환경 수동 확인(D)

| ID | 요구사항 | 우선순위 | 상태 | 구현 · 검증 |
|---|---|---|---|---|
| F1 | TXT·PDF·DOCX에서 텍스트를 추출한다 | 필수 | ✅ | `extract.py` · T |
| F2 | 텍스트를 확보할 수 없는 파일(OCR 신뢰도 미달, 손상 파일 등)은 모든 수신자에게 차단한다 | 필수 | ✅ | 규정 7-1 · T |
| F3 | 정형 개인정보(주민·외국인등록번호, 여권, 운전면허, 카드, 계좌, 휴대폰, 이메일)를 탐지한다 | 필수 | ✅ | `detect.py`, Luhn·생년월일·키워드 검증 · T, M(`eval_detect`) |
| F4 | 문장 속 민감정보(건강·신념·정치·노조·사생활)를 AI로 판단한다 | 필수 | ✅ | `sensitive.py` · T(가짜 LLM), M(`eval_sensitive`) |
| F5 | AI 판단 근거가 원문에 없으면 버리고, AI 호출 실패 시 보수적으로 처리한다 | 필수 | ✅ | fail-closed · T |
| F6 | 수신자마다 개별 판정한다 (수신자 유형 × 정보 유형 → 허용/마스킹/차단 + 근거 조항) | 필수 | ✅ | `policy.py`, `rules.json` · T |
| F7 | 마스킹 대상 수신자에게는 마스킹 사본을 만들고 미리보기를 보여준다 | 필수 | ✅ | `mask.py` · T, D |
| F8 | 판정 이유를 사내 규정 조항을 근거로 자연어로 설명하고, 보낼 수 있는 대안을 제시한다 | 필수 | ✅ | RAG: `retrieve.py` + `explain.py` · M(`eval_retrieval`, `eval_explain`) |
| F9 | AI 설명의 인용 조항·인용문·조치를 검증하고, 틀리면 정확한 기본 설명으로 대체한다 | 필수 | ✅ | 5중 검증 · T, M(20/20) |

## 5. AI 기술 적용 (필수 기술 요소 2개 이상)
| 기술 요소 | 적용 | 왜 필요한가 |
|---|---|---|
| **자동화 Workflow** | 추출 → 정규식 탐지 → AI 판단 → 규칙 판정 → 마스킹 → 설명 → 서명 토큰 → 전송 → 수신 검증 → 감사 로그 | 사람이 매번 하던 확인·판단·기록을 전송 과정 안에 자동으로 넣음 |
| **RAG** | 사내 정보보호 규정에서 BM25로 근거 조항을 검색 → 검색된 조항만으로 설명 생성 → 인용 검증 | 규정은 회사마다 다르고 바뀜 → 모델이 외운 지식이 아니라 그 회사 규정을 근거로 설명해야 신뢰 가능 |

**AI Agent로 주장하지 않는 이유:** 보안 판정을 AI가 스스로 결정하면 결과를 재현·감사할 수 없다. 그래서 판정은 규칙표(결정적)가 하고, AI는 규칙으로 할 수 없는 두 가지(문맥 판단, 설명)만 맡기고 그 출력도 코드로 검증한다.

## 6. 범위 밖 (이번 프로젝트에서 하지 않는 것)
- 손글씨 OCR, 개체명 인식(NER) 모델 학습, 자율 Agent 구조, 데스크톱 앱·PC 에이전트(로드맵)
- 실제 기업 데이터 사용 — 모든 조직·규정·개인정보는 가상 기업 "코데브솔루션(주)"의 가짜 데이터
