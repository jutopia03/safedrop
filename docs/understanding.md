# 단계별 핵심 정리 (발표·아키텍처 문서 재료)

## S1. 뼈대 + 가상 기업 데이터
1. **판정은 LLM이 아니라 규칙표(`data/company/rules.json`)로 결정한다.** "정보 유형 × 수신자 유형 → 조치 + 근거 조항" 표라서 같은 입력엔 항상 같은 결과가 나오고, LLM 환각이 판정에 영향을 줄 수 없다. (멘토 피드백: 근거 조항 환각 대응)
2. **수신자 유형은 4가지**: 개인정보취급자(PRIVILEGED) / 같은 부서(SAME_DEPT) / 다른 부서(INTERNAL) / 외부(EXTERNAL). 조직도(`org.json`)의 부서·권한·외부 여부로 자동 결정된다. 같은 파일도 받는 사람에 따라 조치가 달라지는 이유가 이것이다.
3. **내용을 읽을 수 없는 파일은 차단한다(fail-closed, 규정 7-1).** OCR이 없는 MVP에서도 스캔 문서가 "개인정보 없음"으로 통과되지 않게 하는 안전장치다.

## S2. 텍스트 추출 + 정규식 탐지 (v0 베이스라인)
1. **형식이 정해진 개인정보만 규칙으로 잡는다**: 주민·외국인등록번호, 여권, 운전면허, 카드, 계좌, 휴대전화, 이메일. 이름·주소·건강정보 같은 비정형 정보는 v1에서 LLM이 맡는다. "규칙이 확실한 건 규칙으로, 애매한 것만 LLM으로"가 하이브리드 구조의 의미다.
2. **모양만 보지 않고 검증해서 오탐을 줄인다**: 카드번호는 Luhn 검사, 주민번호는 앞 6자리가 실제 날짜인지 검사(2020.10 이후 번호는 체크섬이 없어 쓰지 않음), 여권·계좌는 바로 앞에 '여권'·'계좌/은행명' 같은 키워드가 있어야 인정. 회사 대표번호 같은 유선전화는 개인 연락처가 아니므로 제외한다.
3. **PDF에서 글자가 거의 안 나오면(페이지당 20자 미만) 스캔 문서로 보고 '검사 불가'로 표시한다.** 이후 판정에서 차단된다(규정 7-1). 성능은 `scripts/eval_detect.py`로 테스트 문서 세트에 대해 재현율(놓친 비율)·정밀도(잘못 잡은 비율)를 잰다.

## S3. 규칙표 기반 수신자별 판정 + 마스킹
1. **수신자마다 따로 판정한다.** 수신자 유형(외부 > 개인정보취급자 > 같은 부서 > 다른 부서 순으로 결정)과 파일 속 정보 유형마다 규칙표에서 조치를 찾고, **가장 엄격한 조치가 그 수신자의 최종 결과**가 된다. 예: 주민번호·계좌·연락처가 든 인사 문서를 영업팀원이 보내면 인사팀=원본, 영업팀 동료·개발팀=마스킹본, 협력사=차단.
2. **모든 판정에 근거 조항 원문이 붙는다.** 조항 원문은 `policy.md`에서 `[3-2]` 같은 ID로 직접 읽어 오므로, 존재하지 않는 조항이 근거로 나올 수 없다. 읽을 수 없는 파일은 모든 수신자에게 차단(7-1).
3. **마스킹은 알아볼 만큼만 남긴다**: 주민번호는 생년월일+성별 자리, 휴대폰은 앞3·뒤4, 카드는 앞4·뒤4, 계좌는 뒤4. 해당 수신자에게 '마스킹'인 유형만 가리고 '허용'인 유형(예: 사내 직원에게 연락처)은 그대로 둔다. MVP는 원본 형식 대신 **텍스트 사본**으로 만든다(한계, 개선 대상).

## S4. 전송 허가 토큰 + P2P 전송 + 화면
1. **전송 버튼을 누르면 서버가 판정을 다시 한다.** 화면이 보낸 결과를 믿지 않는다(클라이언트 조작 방지). 차단이 아닌 수신자마다 **전송 허가 토큰**을 발급한다: {전송ID, 발신자, 수신자, 조치, 파일명, 보낼 내용의 SHA-256, 만료(10분)}를 서버 개인키로 ECDSA P-256 서명.
2. **수신자 브라우저가 직접 검증한다**: ① 서버 공개키로 서명 확인 ② 받은 파일 해시 = 토큰 해시 ③ 수신자 = 나 ④ 만료 전. 하나라도 틀리면 다운로드를 막는다. 테스트: '깨끗한 파일'로 허가받고 개인정보가 든 파일로 바꿔 보내면 해시 불일치로 거부됨을 확인.
3. **전송은 WebRTC P2P가 기본, 실패하면 서버 중계.** 연결 중개(신호)는 우리 서버의 WebSocket이 맡고 파일 자체는 브라우저끼리 직접 전달된다. 수신자가 접속 중이 아니거나 8초 안에 연결이 안 되면 서버 메모리에 최대 10분 두었다가 수신 즉시 삭제한다. 판정·전송·검증 결과는 내용 없이 메타데이터만 감사 로그에 남는다(8-1). MVP 단순화: 로그인 대신 '나는 누구' 선택, 서명 키는 서버 시작 시 생성.

## S5. 배포
1. **Render 무료 웹 서비스에 Docker로 배포**했다(카드 불필요, WebSocket·HTTPS 지원). 같은 Dockerfile로 다른 호스팅에도 그대로 옮길 수 있다. 무료 플랜은 15분 미사용 시 잠들고 깨는 데 약 1분 → 시연 전에 미리 접속.
2. **실제 배포 환경에서 PC↔휴대폰(LTE) 전송과 수신 측 검증 통과를 확인**했고, 미접속 수신자는 나중에 접속했을 때 중계된 마스킹본을 받았다.
3. 베이스라인(v0) 수치는 팀원 테스트 문서 세트로 `scripts/eval_detect.py`를 돌려 기록한다.

## S6. v1: 문맥형 민감정보를 LLM이 판단
1. **문서 전체를 보내지 않고 '후보 문장'만 보낸다.** 건강·종교·정치·노조·사생활 주제 단어가 든 문장만 골라 바로 앞 문장(문맥)과 함께 번호를 붙여 한 번에 묶어 보낸다 → 토큰 한도·청크 분할 문제를 피하고 비용을 줄인다(멘토 피드백 3). 대신 주제 단어가 없는 민감 문장은 놓칠 수 있다(평가 스크립트가 '후보 탈락'으로 따로 센다).
2. **LLM 답을 그대로 믿지 않는다.** 근거 구절(evidence)이 원문 문장에 글자 그대로 없으면 버린다(환각 방지, 멘토 피드백 4). LLM은 '민감정보인가'만 답하고, 허용·마스킹·차단은 여전히 규칙표가 정한다. 호출이 실패하면 후보 문장을 민감정보로 간주한다(fail-closed).
3. **LLM 교체형 구조**: OpenAI 호환 API 하나로 코디세이 중계 서버(gpt-5-mini)와 로컬 GPU의 Ollama를 설정(.env)만 바꿔 오간다 → 온프레미스 전환 근거(멘토 질문 2). 키가 없으면 v0(규칙만)으로 동작. **배포 환경에서 실제 확인**: '공황장애 진단' 문장만 HEALTH로 잡히고 '전 직원 건강검진 공지'는 후보에서 제외, 다른 부서 수신자는 6-3으로 차단.

## S7. v2: 근거 조항 검색(RAG) + AI 설명 + 인용 검증
1. **검색(R)**: 규정 조항을 BM25 키워드 검색(한국어는 글자 2-gram)으로 찾는다. 검색어는 LLM이 만들지 않고 '정보 유형 + 수신자 유형'으로 정해진 문구를 쓴다. 20가지 상황에서 정답 조항이 상위 3개 안에 드는지 측정: **키워드 검색만 90% → 조 제목 태그 필터 추가 100%** (Recall@1 70% → 95%). 단, 규정이 우리가 만든 작은 문서라 높게 나온 수치다.
2. **생성(G) + 검증**: 검색된 조항만 근거로 주고 LLM이 수신자별 2~3문장 설명과 대안을 쓴다(수신자 전체 1회 호출). 코드로 ① 검색된 조항만 인용 ② 규칙표의 필수 조항 포함 ③ 인용 문구가 원문과 글자 그대로 일치 ④ 실제 조치를 언급했는지 확인하고, 하나라도 틀리면 **항상 정확한 기본(템플릿) 설명**으로 대체한다 → 틀린 설명이 사용자에게 나갈 수 없다.
3. **역할 분리**: 판정(허용·마스킹·차단)은 규칙표, '민감정보인가'는 LLM(S6), '왜 그런지 설명'은 RAG+LLM(S7). 필수 기술 요건은 **Workflow(추출→탐지→판단→판정→설명→토큰→전송) + RAG** 2가지로 충족. LLM이 도구를 스스로 고르는 Agent 구조는 아니므로 Agent라고 주장하지 않는다. 측정은 배포 서버의 `/api/eval/{detect|retrieval|sensitive|explain}`로 실행.
4. **실제 배포에서 확인 후 개선**: gpt-5-mini 설명 3건 모두 인용 검증 통과. 다만 검증이 잡지 못하는 문제 2가지를 발견 → ① 아직 검사 단계인데 "전송했습니다" 같은 과거형 ② 다른 부서 차단 건에 규정상 불가능한 "마스킹 사본" 대안 제시. 프롬프트에 시제 규칙과 "검색된 조항이 허용하는 대안만" 규칙을 추가해 수정.
